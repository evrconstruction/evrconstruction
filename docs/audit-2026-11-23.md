### F1 — summary contradicted the findings on the same run

`monday-keywords.ts` recomputed the page-1 count locally (`keywords.filter(position <= 10)`), which
includes queries that are **not ours** — competitors and misspellings such as `evr` (#3),
`ev construction` (#4) and `evp construction` (#6). The findings list below it counts only branded or
service queries.

Measured on the 2026-11-09 run: summary said **6 ranking in the top 10**, the finding said **3**.

`analyzeKeywordOpportunities()` now returns a `stats` object and the skill builds its summary from it,
so the two cannot disagree. Regression test added using the real data set, where `ever construction`
(#6, another company) must not inflate the count.

### F2 — meta descriptions were cut off, and nothing checked for it

Live lengths at the time of the check:

| Page | Description |
|---|---|
| `/projects/decks` | 200 |
| `/projects/patios-pergolas` | 188 |
| `/projects/gazebo` | 180 |
| `/projects/remodeling` | 178 |
| `/projects/restoration` | 174 |
| `/projects/carpentry` | 164 |

Google writes its own snippet past roughly 160 characters. **Root cause:** the metadata reused
`service.summary`, which is also visible copy on the `/projects` cards and ends with
"View our collection of … projects." — so trimming it would have changed the public design.

Fixed without touching any visible copy: each service gained a `metaDescription` field (124–145
characters) used **only** by `generateMetadata`. `summary` still drives the cards and JSON-LD.
The Wednesday audit now has a `dir-audit-description-long-*` rule at 160 characters, so this cannot
regress silently. `PageFacts.hasDescription: boolean` became `description: string` — the length is
what the rule needs, and a separate boolean duplicated it.

### F3 — a malformed data URL became the post image

`api/admin/posts/route.ts` matched `src.startsWith("data:image")`, then only did anything if the
base64 regex also matched. When it did not, `storagePath` stayed empty and
`src: storagePath || src` wrote the **entire data URL** into the post document.

Fixed by extracting `parseDataImageUrl()` into `lib/posts.ts`: no match → HTTP **400**, checked before
any Storage or Firestore call. Three tests cover the malformed forms (`…;base64`, empty payload,
`charset=` variant) and a plain URL.

## 3. DMARC — the report the owner supplied

`google.com!evrconstructions.com!1794960000!1795046399.zip` → report for **2026-11-18 (UTC)**.

```
policy_published: p=quarantine sp=quarantine pct=25
record: source_ip 101.44.1.251, count 1
        disposition none   (reason: sampled_out)
        dkim fail, spf softfail
```

- `101.44.1.251` resolves to `ecs-101-44-1-251.compute.hwclouds-dns.com` — **Huawei Cloud**, a
  rented host. It is spoofing the domain; no legitimate sender uses it.
- `disposition: none` with reason `sampled_out` is the `pct=25` policy working as configured: the
  message fell outside the sampled 25%, so nothing was quarantined.
- **No legitimate sender failed.** Google's own mail was not in this report at all, and every
  report since 2026-10-22 has shown Google passing with aligned DKIM (`selector google`) and SPF.

DNS measured today: exactly **1** DMARC record, exactly **1** SPF record, MX `smtp.google.com`,
`google._domainkey` and `resend._domainkey` published, nameservers GoDaddy.

**Phase 2 is overdue.** It was due around 2026-11-03; the record still reads `pct=25`.
`EMAIL_FROM` is still `onboarding@resend.dev`, so no application mail is sent as the domain and
enforcement cannot affect it.

## 5. Left in place on purpose

`npm audit` still reports **4 moderate** advisories, all one chain:

```
@google-cloud/firestore@9.1.0 → @google-cloud/firestore-api@0.2.0 → google-gax@5.0.8
  → rimraf@5.0.10 → glob@10.5.0 → minimatch@9.0.9
```

Clearing them requires `@google-cloud/firestore` **9.4.1** (which uses `firestore-api ^0.7` →
`google-gax ^6`). That was **not** applied here:

- the vulnerable code is `google-gax`'s `compileProtos` tooling — no request path in this app passes
  user input to `glob` or `rimraf`;
- the upgrade would move the **Firestore client used by every project gallery**, the site's most
  important runtime path, by three minor versions with no local test coverage (this account cannot
  read Firestore — `403` measured today);
- `npm audit fix` would force it as an unplanned change, which is exactly how `next` was silently
  bumped in a previous pass.

The upgrade is available and safe to do deliberately: `npm update @google-cloud/firestore`, then
confirm `/projects/decks` still renders its Firestore-backed images after the rollout.
