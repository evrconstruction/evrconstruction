### F3 — a malformed data URL became the post image

Fixed by extracting `parseDataImageUrl()` into `lib/posts.ts`: no match → HTTP **400**, checked before
any Storage or Firestore call. Three tests cover the malformed forms (`…;base64`, empty payload,
`charset=` variant) and a plain URL.

## 9. Personal address removed, Bizapedia explained — 2026-11-23

### 9a. The published address was the owner's home — removed

**Owner statement, 2026-11-23:** the business has no storefront; `3417 Mynatt Rd` is a **personal
residence**. It must not be published.

Where it actually appeared — **one place only**, the homepage's `LocalBusiness` JSON-LD. It was
never rendered as visible page text (no page prints it, and the contact page carries no address), so
this change alters **nothing visible**.

| | before | after |
|---|---|---|
| `address.streetAddress` | `3417 Mynatt Rd` | **absent** |
| `address.addressLocality` / `Region` / `postalCode` | Knoxville / TN / 37918 | unchanged |
| `geo` | `35.9606, -83.9207` (downtown Knoxville) | **removed** |
| `areaServed` | 15 cities | unchanged |

**Why `geo` was removed too.** Coordinates are optional in schema.org, and the previous value was
downtown Knoxville — roughly 10 km from the address it sat beside. With no premises to describe,
publishing a point would assert a location the business does not have. `areaServed` is the honest
geographic signal and was already present.

Verified by rendering the built site: the homepage still emits **4 JSON-LD blocks**, `areaServed`
still lists **15** cities, the string `Mynatt` appears **nowhere** in the HTML, and the ZIP `37918`
remains (city-level, not a household locator).

**The audit had to change with it**, or the next Wednesday run would have reported the schema as
broken:

- `REQUIRED_BUSINESS_FIELDS` no longer includes `geo`. This is **not** lowering the bar — `geo` is
  optional in schema.org and demanding it from a service-area business pushes whoever maintains the
  schema towards inventing a location. Coordinates are still **read and reported** if a future
  schema publishes them; they are simply not required.
- `describeField()` now renders a locality-only `PostalAddress` as `Knoxville, TN, 37918` instead of
  returning an empty string.
- `hasStreetAddress` distinguishes the two forms, so the coordinates caveat only says "compare against
  the street address" when one exists. With no address it now states that the city/ZIP-only form is
  *expected* for a service-area business, so the absence does not read as a gap.

Five tests in `tests/lib/wednesday-schema.test.ts`. **Proven non-vacuous:** reverting the
`addressLocality` branch makes `accepts a locality-only address` fail.

## 12. 🔴 `evrconstruction.com` is a different company, but the verifier treats it as ours

Found while investigating the DNS question. **Not fixed — needs an owner decision, because it changes
backlink reporting.**

`src/lib/integrations/backlink-verifier.ts:56`:

```ts
const BRAND_HOSTNAMES = ["evrconstructions.com", "evrconstruction.com"];
```

The **singular** domain is not this business. Measured 2026-11-23:

| | `evrconstructions.com` (ours) | `evrconstruction.com` (singular) |
|---|---|---|
| Registered | 2026-07-22 | **2012-02-16** |
| Registrar | Wild West Domains (GoDaddy) | PDR Ltd. / PublicDomainRegistry.com |
| Nameservers | `ns11/ns12.domaincontrol.com` | `ns1/ns2.md-in-70.bigrockservers.com` |
| A record | `35.219.200.198` (our App Hosting LB) | `103.53.40.81` |
| Serves | EVR Construction LLC, Knoxville TN | **"EVR Construction \| Kancheepuram"** |
| DMARC | published | none |

`Kancheepuram` is a district in Tamil Nadu, India. The page contains no reference to Knoxville,
Tennessee or EVR Construction LLC — it is an unrelated namesake that has held the name since 2012.

### Why it matters

`pointsAtThisSite()` feeds `detectBrandLinkRel()`, which scans a directory page for the anchor pointing
back at us and reads **that anchor's** `rel`. A directory listing for the Indian company would
therefore have its `rel` reported as *our* verified backlink type.

`BRAND_MENTIONS` compounds it: the entry `"evr construction"` matches the Indian company's name, so
`classifyServedPage()` would call such a page `Active` — a false "your citation is live" for a business
that is not ours.

**Practical exposure today is low:** the six tracked citations are Houzz, BBB, Bizapedia, Nextdoor,
Yelp and Thumbtack, none of which list an Indian contractor. The defect is latent, not currently
producing a wrong number.

### Fix, once approved

Remove the singular entry, leaving only the domain this business owns:

```ts
const BRAND_HOSTNAMES = ["evrconstructions.com"];
```

Worth a test asserting that a link to `evrconstruction.com` is **not** counted, so the two domains
cannot drift back together. Confirm first that the owner does not hold the singular domain under a
different account — everything measurable says it belongs to someone else, but a domain is not
something to assume.
