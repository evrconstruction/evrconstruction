### F1/F2 — Next.js critical + the blind spot that hid it
`next@16.3.8` was in range for:

- `GHSA-2464-fhr4-w9xw` — **critical, CVSS 9.5**, unauthenticated RCE via the image-optimisation
  API when SVG is used. Patched in **16.4.1**.
- `GHSA-673q-mjm6-r5xr` — **critical**, RCE in `use cache` returning typed arrays.
- `GHSA-p3m5-59mp-jv5r` — high, DoS in App Router Server Actions.

**Real exposure was low, measured not assumed:** `sharp` is 0.35.5 (meets the advisory's own
workaround), `grep '"use cache"|"use server"' src/` returns **0 hits**, and no `/_next/image` URLs are
emitted in the live HTML (probing `/_next/image` directly → 404), so the optimizer route was not exposed.

**Why it was invisible:** `next` sat in `devDependencies`. Production never loaded it from that tree —
App Hosting builds Next as tooling — but `npm audit --omit=dev` therefore reported a clean production
tree while Next itself carried a CVSS 9.5. Dependabot did not list it either. **This is fixed:** `next`
now lives in `dependencies` and `eslint-config-next` was moved to match at 16.4.3.

### F3 — a live listing reported as gone
Tuesday's 2026-10-27 run recorded *"Bizapedia …: Listing is gone (HTTP **200**)"* — a self-contradictory
verdict. The listing is live: HTTP 200, `<title>EVR CONSTRUCTION LLC in Knoxville, TN …>`, the company
name appears 6× and the address `3417 MYNATT RD LOT 73` is present.

**Root cause:** `backlink-verifier.ts` mapped *2xx with no brand string* → `"Missing"`. `Missing` means
"the listing is gone" and raises a **High** directive telling the owner to claim or rebuild it.
A 2xx proves only that *something* was served — directories answer automated requests with consent
walls, script shells and regional variants that never name the business. **`Missing` is now reserved for
404/410**, the only statuses that actually state a listing is gone. An unreadable 2xx is `Blocked`
("could not be read"), and the finding text now says so.

Extracted `classifyServedPage()` (pure, exported) plus `BRAND_MENTIONS`, covered by 4 new tests
including the exact regression (consent-shell body → `Blocked`) and the empty-body case.

### F4 — soft 404 on unknown project slugs
`GET /projects/nonexistent-slug` → **200**, canonical pointing at the invented URL, and two
contradictory robots tags (`index, follow` **and** `noindex`). The page component does call
`notFound()`.

**Root cause, proven locally:** the segment has a `loading.tsx`, so a **200** Suspense shell streams
before the page body runs; `notFound()` then swaps the 404 UI into an already-committed 200. Verified by
removing the boundary and rebuilding — the same URL then returned a true **404**.

Partial fix shipped: the slug is now rejected in `generateMetadata`, so it resolves before the shell is
sent and the 404 page carries `Page Not Found` instead of the generic `Project Collection` fallback.
**The status itself still depends on `loading.tsx` — see §5.**

## 5. Open items needing the owner

### 5.1 Soft-404 status (needs one-word approval)
The confirmed cause is `src/app/(site)/loading.tsx`. Deleting it makes unknown slugs return a true **404**.

The argument for deleting it: in the route table, `/`, `/about`, `/projects` and `/contact` are all
**static** — the loading boundary has no effect on them. It only ever applies to `/projects/[slug]`, the
single dynamic page, **which is precisely the page it breaks**.

The argument against: it is a visible UI element, and the public design is frozen by standing rule — so
this needs explicit approval either way. Practical urgency is low: Google reports 0 indexing problems and
no invented URL is in the index today.

### 5.2 Bizapedia directive `dir-cit-lost-op4oo4Ry4rBWMinzLH8p` — **leave it open**
"Fix Broken Citation: Bizapedia Tennessee", **High, Open**, created 2026-10-20.

It was initially assessed as a pure false positive and slated for closure. **That was wrong** once the
listing's contents were read: the profile records the website as `"https://https://evrconstructions.com"`
— a malformed double scheme — inside structured data, with **no proper anchor** to the site. So the
listing is live but is **not a functional backlink**. The "gone" wording was wrong; the underlying gap
is real. It is therefore **deliberately left Open** and needs a manual fix on Bizapedia (§6.3).

Note this directive will **not** self-resolve: resolution only fires on `Active`, and production now
records `Blocked` for it. It ages out via `STALE_DIRECTIVE_DAYS = 30` around **2026-11-19**.
